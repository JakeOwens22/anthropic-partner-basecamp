Participant Guide

You are building Larkspur's chat agent for customers whose flights are disrupted, over two sessions, in a repo your team owns. This guide is the path: what to do, and how you will know it worked.

You are the team Larkspur Airlines brought in. Session one has two builds: you fix the agent you are given, then give it a tool of your own. Session two has two more: you build the proof of what the agent does, then move one number on purpose and prove it moved.

Every build step follows the same pattern. Read the block labeled "You will know it worked when" first.

agent.py is the file you edit. Everything under support/ already works, and you never edit it. verify.py is the check you run at the end of every step, and it decides whether the step is done. It never looks at how you wrote your code, only at what your agent sent to Claude and what came back, so everyone in your team can write different code and all of them can pass.

Nothing in here hands you an answer. The trace is your debugger. Run it, read what came back, change one thing, run it again.

The same steps live on the build site, which your team opens together in the room. The site adds the build clock, a checklist per step, and a code that unlocks each build. This document is the same path on paper.

The client's issue

  • Larkspur is a US carrier with about 19 million passengers a year and 1,150 people in the contact center.
  • Larkspur gets about 4.2 million contacts a year. Disruption is 31% of them and 52% of contact-center cost.

  • A human-handled contact costs them $6.90.

1.1

Read the trace, find the four faults

What you are building

By the end of this step you have read the trace and written a list of what you found. You build nothing yet.

The habit is to sort them by what you would fix first. Run the agent, read the wire, name what is wrong in that order. On a client's codebase this is all you get.

Do
  1. Start the demo server in its own terminal tab and leave it running there. It does not return; that is what running looks like.
    $ python3 demo/serve.py
  2. In a second tab, or a browser, open the demo and send K7PQ2M one message. Every step from here ends by sending the same message again.
    $ open http://localhost:4390
  3. Run one ticket with the trace on and read it top to bottom. Read every TURN line, in order.
    $ python3 run.py K7PQ2M --trace
  4. Ask the trace two questions. Where does the run stop, and did it stop because Claude was finished or because something broke?
  5. Read the error line above the trace to its last word if a turn came back as an error. The sentence naming what the API would not accept is usually the second one.
  6. Read the answer run.py prints above the trace, not only the turns. A run that ended properly and said nothing is still a failure.
  7. Read what each tool ANSWERED on the ↩ line under each ⚙ line. -v prints up to 500 characters of each reply.
    $ python3 run.py K7PQ2M --trace -v
  8. Read what Claude receives about each tool: the descriptions and the fields inside each input schema.
    $ python3 run.py --show-tools
  9. Find the two entries of the nine that are wrong. One description is thin where it should be a sentence, and one field tells Claude the wrong thing about what to send.
  10. Write what you found in two columns: SEEN, what the trace and what Claude receives about each tool showed you and which function owns each one, and PREDICTED, one line on what is hiding behind the thing that stopped the run. Compare both columns with a teammate.
You will know it worked when

Your list has symptoms, not fixes, and a prediction. Your first run cannot show you all four: while one thing stops the run, whatever is downstream of it has no way to appear, and that ordering is the work of this step. So the deliverable is what you saw plus what you expect, and step 1.2 is where you find out whether the prediction held. This list is yours, so here is the layout rather than the content.

1.2

Make the loop keep going

What you are building

The loop is the agent. Everything else is a description Claude reads or a function it calls.

stop_reason is the one field that says whether Claude is done or waiting on a tool. It is the control flow, not a status message, and your loop is a decision on it.

Do
  1. Run it and read turn 2. That is where the first fault lives.
    $ python3 run.py K7PQ2M --trace
  2. Open agent.py and print the six places you edit. The loop sits at the top under three empty slots, and the nine tool schemas are below the ruled line.
    $ grep -n '✏️' agent.py
  3. Change one thing in run_agent(), then run it again. Never make two changes at once.
  4. Keep going until the same run ends on stop_reason=end_turn and prints a non-empty answer above the trace.
  5. Then run the gate. A gate here is a verify.py check.
    $ python3 verify.py 1.2
  6. Back in the demo, send K7PQ2M the same message as before and watch a full answer come back where the card was.
You will know it worked when

Which grader to reach for

Two habits matter before you ship a judge. Make it quote what it read, and never let a model grade its own output.

eval_harness.py holds itself to the second one. Your agent runs on the model support/data.py names. The judge runs on claude-opus-4-8, a more capable model, and that is on purpose. A judge on the same model id as the agent has the same blind spot as the model that wrote the answer, and reads its own phrasing back as correct. The judge is more capable rather than less, because catching a fluent reply that contradicts the tool result it was handed is the one thing a judge is for. It costs more per case and it is slower, and that is this grader's charge, printed in the header of every run. You swap it by setting one environment variable, and diffing the verdicts is the fastest way to see what your rubric actually rests on.

And suspect the eval first. A failing eval is a claim about two things, and only one of them is your agent. In Larkspur's week 8, one suite fell to 37 passes out of 48 in a single night. Here is the rule, in one sentence. Nobody commits agent.py mid-build. At the end, the build's committer publishes the canon and everyone else takes it.

$ python3 pod_sync.py --push-canon --note "what changed and why"   # the committer
$ python3 pod_sync.py --take-canon   # everyone else

Everyone builds their own agent.py on their own laptop. Several people editing one file in one repo at the same time produces a merge conflict inside a loop they are all still learning to read, and no build has time for that. So the repo only ever holds one version: the one the team chose.
